# Menu App Web Editor: Complete Development Guide & Post-Mortem

## Overall Objective
Build a completely client-side, zero-server Single Page HTML app (`index.html`) that replicates an extremely specific Dine-In Menu graphic (`menu-bg.png`). The text fields (items, prices, notes) mapped directly over the background graphic must be inline-editable, savable via LocalStorage, and exportable perfectly to both a PDF and a high-resolution 300 DPI PNG file matching the original graphical source truth.

---

## Part 1: Pixel-Perfect Coordinate Mapping

### ❌ What Failed: Automatic PDF Text Extraction & Relative Ratios
**The Problem:** Initially, we tried extracting the structural coordinates from the provided `menu-text-reference.pdf` programmatically using Python `PyMuPDF (fitz)` and applying them natively to a responsive `850x1400px` container.
**Why it failed:** 
1. The physical aspect ratio of the structural PDF (`0.68`) completely misaligned with the arbitrary 850x1400 browser container layout (`0.60`). This caused the CSS text to severely stretch or squish relative to the background image.
2. The coordinate extraction grouped text strangely (e.g. mashing names and prices together), resulting in massive overlaps and broken bounding boxes that were completely unreadable.

### ✅ The Solution: Native PDF Aspect Ratio & Explicit Manual Mapping
Instead of relying on fuzzy programmatic extraction:
1. We forced the `index.html` CSS container to mathematically exactly match the PDF's native internal dimensions (`width: 908px; height: 1336px;`). This instantly cured all aspect ratio stretching and distortion.
2. We generated a bare-metal JSON array (`raw_coords.json`) dumping every structural word and their absolute X/Y points. 
3. We wrote a targeted Python script that *exactly* mapped explicit strings (e.g. `"Oxtails w/Rice & Gravy"`) directly to specific Data-Keys (`main_oxtails`), abandoning programmatic grouping entirely. This decoupled the text perfectly, splitting out titles, items, notes, prices, and even missing Chef's features seamlessly.
4. CSS nudges for edge cases like small "EVERY OTHER WEEKEND" notes were manually hand-tuned down to the decimal.

## Part 2: The "Tainted Canvas" CORS Error on PNG Export

### ❌ What Failed: Standard html2canvas Implementation
**The Problem:** The user hit a `SecurityError: Failed to execute 'toDataURL' on 'HTMLCanvasElement': Tainted canvases may not be exported`.
**Why it failed:** Modern browsers (Chrome, Edge, Safari) strictly enforce Cross-Origin Resource Sharing (CORS) policies. When running an `index.html` file locally from a hard drive (`file:///C:/...`), Javascript (`html2canvas`) is permanently blocked from internally copying or saving visual arrays of any *external local image files* (like `menu-bg.png`) due to security privacy lockdowns.

### ✅ The Solution: Base64 String Injection
Since the browser blocks external hard drive `file://` linking, we bypassed the file system load entirely. We wrote a script that opened `menu-bg.png`, converted it perfectly into raw text data (Base64 encoding), and permanently baked that massive data string directly into the inner HTML structure as an `src="data:image/png;base64,iVBORw0KGgoAAA..."` source string. Because the image now officially lives *inside* the HTML code string, the browser no longer flags it as an external local security fetch, and immediately permits perfectly clean PNG exporting.

## Part 3: Blurry Background Image on PNG Export

### ❌ What Failed: CSS Background Image Property
**The Problem:** After bypassing the Security Taint error, the image exported perfectly, but the background photos (the food and brick background) were heavily pixelated, compressed, and blurry, while the text itself remained perfectly sharp. 
**Why it failed:** `html2canvas` inherently mishandles CSS `background-image` layout sizing. When rendering the page for the virtual screenshot, the html2canvas engine forcibly down-samples the original massive 5000+ pixel source background into the visual 908px layout container *first*, and then attempts to scale it back up for export, irrevocably obliterating the high-res data.

### ✅ The Solution: Raw DOM `<img>` Injection
We surgically removed the CSS `background-image` property entirely. Instead, we injected the massive Base64 data string into a hidden, non-interactive `<img>` DOM node absolutely positioned natively behind the text. By rendering it as an actual physical DOM element instead of a CSS property, `html2canvas` utilizes the original full-spectrum uncompressed image payload during its 4x scaling export multiplier, curing background image compression.

## Part 4: Forcing 300 DPI File Output Metadata

### ❌ What Failed: Simple Scale Multipliers & Base Image Resizing
**The Problem:** The exported PNG was huge and sharp, but checking the image size in Photoshop exposed that it was tagged as **72 DPI**. The user required identically matching 300 DPI exports strictly equivalent to modern print workflows.
**Why it failed:** `html2canvas` does support visual pixel scaling (via `scale: 4,` multiplier config to generate physically larger images). However, **standard web browser engines are permanently hard-coded to assign 72 DPI (web native standard) metadata chunks** to any Canvas API image files generated natively inside the browser context, regardless of their actual physical pixel dimensions. Bumping the internal canvas scale to larger physical sizes simply makes a larger 72 DPI file.

### ✅ The Solution: Manual Binary PNG Data Rewriting via Javascript
Because the browser strictly refuses to encode a 300 DPI chunk natively from the Canvas API, we physically intercepted the finished chunk of image data *in the fractional second between html2canvas generation and the user's hard drive download interface*.
1. We intercepted `canvas.toBlob()`.
2. We deployed a sophisticated binary re-writer function (`changeDpiBlob()`).
3. This function rips open the raw `Uint8Array` binary byte data of the generated PNG file inside terminal browser memory.
4. It navigates dynamically past the native `IHDR` image header block.
5. It chemically injects a custom `pHYs` standard metadata format chunk perfectly matching the 300 DPI (11811 Pixels Per Meter) specification: `[0, 0, 0, 9, 112, 72, 89, 115, ... 11811 ... 11811 ... ]`.
6. It dynamically recalculates the exact cyclic redundancy check (CRC) checksum required for the chunk for the PNG validation headers.
7. It patches the file back rapidly into an `objectURL` output Blob, natively coercing the operating system and Photoshop into flawlessly reading the generated graphic precisely at exactly **300 DPI**.
