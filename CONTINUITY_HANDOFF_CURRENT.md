## 2. The Golden Rules — Read Before Writing Any Code

These are non-negotiable. Violating any of them will break the project.

### Rule 1: NEVER edit index.html directly
`index.html` is a **compiled artifact**. It is generated by `build_app.py`. Any direct edit to `index.html` will be overwritten the next time `build_app.py` is run. **Always edit `build_app.py`**, then run `python build_app.py` to regenerate `index.html`, then commit both.

### Rule 2: Double all literal braces in Python f-strings
`build_app.py` uses Python f-strings to emit JavaScript and CSS. Any literal `{` or `}` in the JavaScript or CSS output must be written as `{{` or `}}` in the Python source. This is not optional — forgetting it causes Python SyntaxErrors or silent variable injection bugs.

```python
# CORRECT
js = f"const obj = {{key: 'value'}};"

# WRONG — breaks the build
js = f"const obj = {key: 'value'};"
```

### Rule 3: Never load menu-bg.png on page load
`menu-bg.png` is 7.2 MB. It is only loaded during the export pipeline. The editing preview uses `menu-bg-preview.jpg` (~114 KB). Loading the full PNG on page load breaks mobile performance. This split is intentional and must be preserved.

### Rule 4: Layout Locked is always the default on load
The app must always initialize with Layout Locked = true. This is a safety feature for non-technical restaurant staff. Do not change the default to Unlocked.

### Rule 5: User images must be served from the same origin
Cross-origin images taint the HTML canvas and prevent PNG export. All uploaded images must be stored on the Railway Volume and served from `/user-images/<filename>` on the same domain.

### Rule 6: The pHYs DPI injection must not be removed
The `inject300DpiMetadata()` function manually rewrites the exported PNG binary to insert the pHYs chunk (11811 pixels/meter = 300 DPI). Browsers do not add DPI metadata to canvas exports by default. Removing this function produces PNGs that look correct on screen but report 72 DPI to printers and design software.

### Rule 7: html2canvas must remain lazy-loaded
`html2canvas` is a large library. It must only be loaded when the user triggers an export, not on page load. Any refactoring that moves it to a static import will hurt load time.

### Rule 8: Never use native browser alert(), confirm(), or prompt()
The project uses a fully branded custom modal and toast system. Native browser dialogs break the mobile UX and are visually inconsistent. All confirmations and notifications must use `showModal()` and `showToast()`.

### Rule 9: Atomic writes only for server persistence
All writes to `menu_data.json` must use the `.tmp` + `os.replace()` pattern. Never write directly to the final file path. This prevents data corruption on interrupted writes.

### Rule 10: Do not reopen locked architecture decisions
See Section 9 of this document. Those decisions were reached through hard-won debugging and must not be casually reversed.

## 7. Common Pitfalls — Mistakes That Have Already Been Made

These are real bugs that occurred during development. Do not repeat them.

### Pitfall 1: Raw newline in Python f-string (Phase 27-E)
A literal newline character inside a Python f-string emitting JavaScript caused a SyntaxError. Always use `\n` for newlines inside JS strings emitted by Python f-strings.

### Pitfall 2: contentEditable as boolean (Phase 27)
Setting `element.contentEditable = true` (boolean) instead of `element.contentEditable = "true"` (string) breaks text editing in certain browsers. Always use the string form.

### Pitfall 3: Rogue sync() call in onTextBlur (Phase 27-C)
A `sync()` or auto-save call inside `onTextBlur` triggered server saves every time the user finished typing a single character. Removed — `onTextBlur` should only commit text to the data model, not trigger network calls.

### Pitfall 4: Undo snapshot taken after text commit (Phase 22)
`pushState()` was called in `onTextBlur` (after the edit) instead of `onTextFocus` (before the edit). This meant you could not undo a text change — the snapshot already had the new value. Fix: always snapshot state before the user begins editing, not after.

### Pitfall 5: Zoom not restored on Load Session (Phase 27-D)
The Load Session code was updating `state.zoom` but not applying it to the CSS transform of the canvas container. Always call the zoom-apply function after setting `state.zoom` programmatically.

### Pitfall 6: Locked elements getting z-index elevated (Phase 16)
The render function was applying a hover z-index boost to all elements, including locked ones. Locked and background elements must be explicitly excluded from z-index elevation on hover/selection.

### Pitfall 7: Export background not swapping back (Phase 20)
After `html2canvas` captures the export, the background must be swapped back from `menu-bg.png` to `menu-bg-preview.jpg`. If this swap fails silently (e.g., due to an error mid-export), the large PNG remains in the DOM and slows the editor. The export function has a `finally` block to guarantee the swap-back.

### Pitfall 8: html2canvas treating CSS background vs. DOM img differently
`html2canvas` captures CSS backgrounds unreliably. The background MUST be a DOM `<img>` element, not a CSS `background-image` property, for reliable cross-browser capture.

### Pitfall 9: Missing font load before export (Phase 24)
If `html2canvas` runs before custom fonts are fully loaded by the browser, text elements render in the fallback system font. Always await `document.fonts.ready` before calling `html2canvas`.

### Pitfall 10: Multi-line text element height not calculated correctly (Phase 23–24)
When exporting, text element height was calculated using single-line height even when the text contained newlines. The export pipeline must calculate height as `lineCount × lineHeight × fontSize`.
